# 1. No.20 外部Character Sheet対応【確定】

## 1.1 基本方針

いあきゃら／キャラッシュ等の外部Character Sheet Serviceについて、
MVPでは各Serviceとの直接API連携を中心としない。

代わりに、

> **CCFOLIA用の駒データを共通入力補助形式として利用する**

方式を採用する。

## 1.2 Table登録／編集での入力補助

EndPcState入力に、

> **「ココフォリア駒データから入力」**

を追加する。

UserはClipboardへCopyしたCCFOLIA駒データJSONを貼り付ける。

File Upload方式にはしない。

## 1.3 抽出対象

CoC系では、駒データ内のStatusから主に以下を抽出する。

- SAN
- HP
- MP

抽出するのは各Statusの `value` を基本とする。

以下はMVPではEndPcStateへの自動入力対象としない。

- 技能
- Ability
- Memo
- Chat Palette
- Image
- その他CCFOLIA固有Data

## 1.4 保存Rule

CCFOLIA JSONそのものは恒久保存しない。

解析結果は、

> **EndPcState Formへ入力する候補値**

として扱う。

Userが確認・修正した後、
通常のEndPcState保存処理を行う。

Manual入力とCCFOLIA貼り付け入力は共存する。

## 1.5 PCとの関係

Character Sheet URLは従来どおりPCの任意参照情報として保持可能。

ただし、

- SAN
- HP
- MP
- その他現在Status

をPC本体へ現在値として恒久保存しない。

外部DataはTableごとのEndPcState入力補助として使用する。

## 1.6 Failure時

解析失敗はTable登録失敗としない。

UserはそのままManual入力へ切り替え可能とする。

# 2. No.21 UC08「最近使用した情報」の判定Rule【確定】

## 2.1 基本

「最近」は新しい `lastUsedAt` 等の属性を追加せず、
既存のTable / TableDate / Participationから導出する。

## 2.2 使用日時

TableDateが存在する場合：

> そのTableの最新TableDateを使用日時として扱う。

TableDateがない場合：

> Table登録日時を低精度の補助的な順序情報として使用可能。

ただし登録日時を「実際に遊んだ日」とは扱わない。

## 2.3 Person

Personの最近使用判定は、
そのPersonがParticipationとして参加したTableのうち、
最も新しい使用日時を基準とする。

KP用／PL用に別々のRecent RankingはMVPでは作らない。

同じPersonはRecent候補内で重複表示しない。

未使用PersonはRecent候補には含めないが、
通常候補として選択可能。

## 2.4 PC

PC選択は、

1. まずPL / Personを選択
2. そのPersonに現在紐づくPCを通常候補として表示
3. その中で最近使用したPCを優先表示

とする。

現在そのPersonに紐づいていないPCは通常候補には出さない。

ただしSearch / Autocompleteでは、

> **Login User所有の全PC**

を検索可能とする。

別Personに現在紐づくPCを検索結果から選択することも可能。

その場合、
現在のPL / Person名を補助表示する。

Participation.person と PC.person の一致はDB制約として強制しない既存仕様を維持する。

## 2.5 Recent件数

Recent候補は、

> **Person / PCそれぞれ最大5件**

とする。

それ以上はSearch / 通常候補から選択する。

## 2.6 Scenario

Table登録画面ではScenarioはすでにScenario Viewで選択済みのため、
ScenarioのRecent候補は表示しない。

Scenarioの「最近」については、
Homeの既存初期Sort「最近遊んだ順」で扱う。

## 2.7 自動選択

Recent候補は候補提示のみ。

自動選択・自動確定しない。

# 3. No.22 月別／年別集計で日付なしTableをどう扱うか【確定】

## 3.1 集計基準日

月別・年別集計では、
各Tableについて1つの「集計基準日」を算出する。

### TableDateが1件
そのTableDateを使用。

### TableDateが複数
> **最新のTableDate**

を使用。

### TableDateが0件
> **Table登録日時**

を集計基準日の代替値として使用。

## 3.2 重要な意味分離

Table登録日時は、

> 実際に遊んだ日

として保存・表示しない。

あくまで、

> **UC17の月別／年別集計上、所属年月を決めるための代替値**

として使用する。

## 3.3 集計単位

1Tableは必ず、

- 1つの月
- 1つの年

にだけ所属する。

複数日にまたがるTableでも、
月別・年別で重複Countしない。

## 3.4 PL / KP / Scenario

以下も同じ集計基準日を使用する。

- Table数
- PL参加回数
- KP参加回数
- Scenario数

## 3.5 Data構造

`aggregationDate` 等の新しい永続Column / Entityは追加しない。

集計時に算出する。

## 3.6 UC17 CRUD

月別／年別集計の期間判定に必要なため、

> **UC17にTableDate Readを追加**

する。

# 4. No.23 Scenario URL Validation Rule【確定】

## 4.1 基本

Scenario URLは任意。

BOOTH専用にはせず、
以下を含む汎用Scenario参照URLとして扱う。

- BOOTH
- pixiv
- TALTO
- note
- 公式Site
- 作者Site
- その他Scenario紹介／配布Page

## 4.2 許可するURL

保存可能なのは、

- `https://`
- `http://`

の絶対URLのみ。

Hostnameが存在すること。

## 4.3 拒否するScheme

Scenario URLとして以下は拒否する。

- `javascript:`
- `data:`
- `file:`
- `ftp:`
- `mailto:`
- その他HTTP(S)以外

## 4.4 その他Validation

- 前後空白を除去
- 空欄／空白のみは未設定として扱う
- UserInfoを含むURL（例：`https://user:pass@example.com`）は拒否
- Query Parameterは許可
- Fragmentは許可
- 特定Domain Allowlistは作らない
- URLの存在確認は保存時に行わない
- Redirect確認も保存時に行わない

FrontendとBackendの両方でValidationする。

## 4.5 表示

Scenario Viewでは生URLを常時表示せず、

> **「シナリオページを見る ↗」**

等のExternal Linkとして表示する。

## 4.6 BOOTHとの連携

BOOTH補助で商品URLを入力し、
情報取得に成功した場合：

- Scenario URLが空なら、そのBOOTH商品URLをScenario URL候補として仮反映
- Userは変更・削除可能
- 編集時に既存Scenario URLがある場合は無言上書きしない

BOOTH URL専用の正式DB属性は追加しない。

正式保存先は従来どおりScenario.urlのみ。

# 5. No.24 重複Scenario候補の具体判定Rule【確定】

## 5.1 基本

Scenario名 / URLはUniqueにしない既存仕様を維持する。

重複候補は、

> Validation ErrorではなくWarning / Neutral

として扱う。

自動統合しない。

最終判断はUserが行う。

## 5.2 照合範囲

重複照合は、

> **Login Userが所有するScenario内だけ**

で行う。

他UserのScenarioとは照合しない。

## 5.3 強い候補

以下は強い重複候補とする。

### URL一致
同じURLを持つ既存Scenario。

### Scenario名＋作者一致
URLが異なっていても、
Scenario名と作者が一致する場合は強い候補。

BOOTH / pixiv / TALTO等、
同一Scenarioが複数のURLを持つ可能性を考慮する。

## 5.4 確認候補

Scenario名一致のみでも確認候補にする。

Scenario名＋Game System一致は、
作者欠損時等の補強材料として利用可能。

## 5.5 候補にしない条件

以下だけでは重複候補にしない。

- 作者だけ一致
- Game Systemだけ一致
- 同じDomain
- 部分一致のみ

## 5.6 Scenario名の比較用正規化

保存値は変更しない。

重複検索用にだけ、以下程度の軽い正規化を行う。

- 前後空白除去
- 連続空白の統一
- 全角／半角英数字の統一
- 英字大文字／小文字の差を無視

高度なFuzzy Search / AIによる同一作品判定はMVPでは行わない。

## 5.7 URL比較

URL一致判定では、
同じPageであることが明白な差だけ軽く正規化してよい。

例：

- Hostの大小文字
- 末尾 `/`
- Fragment

Query ParameterはPage識別に必要な場合があるため、
安易に削除しない。

URL不一致は、

> 別Scenarioである証拠

とは扱わない。

## 5.8 UI

候補表示では、

- Scenario名
- 作者
- Game System
- Scenario URL
- 関連Table数

等を比較材料として表示可能。

Userは、

- 登録済みScenarioを使う
- 新しいScenarioとして登録

を選択可能。

同名／同URLでも新規登録自体は禁止しない。

# 6. No.25 BOOTH取得処理の具体技術方式【確定】

## 6.1 位置づけ

BOOTH取得機能は、

> **公式API連携**

とは呼ばない。

Userが指定した1商品について、
Scenario登録を補助するための軽量な情報取得として扱う。

## 6.2 取得対象

BOOTH全体を巡回・収集するCrawlerは作らない。

Userが入力した1商品だけを対象とする。

## 6.3 実装経路

FrontendからBOOTHを直接解析しない。

> Frontend → 自Service Backend → BOOTH

とする。

入力されたBOOTH URLから商品IDを抽出し、
Backend側でBOOTH商品Pageを構築して取得する。

任意URLをそのままBackend HTTP Clientへ渡さない。

SSRF対策として、
取得先をBOOTHに限定する。

## 6.4 第一取得手段

> **公開されているBOOTH商品Page HTML**

を第一取得手段とする。

公開Developer APIとして保証されていない内部JSON endpointを、
MVPの正式依存先にはしない。

非公式BOOTH SDKへの必須依存も避ける。

標準的な、

- HTTP Client
- HTML Parser
- JSON Parser

程度で実装する。

Spring Bootの場合の候補：

- WebClient / Java HttpClient
- Jsoup
- Jackson

## 6.5 取得結果

利用候補となる情報：

- 商品名
- Shop名
- Category
- Tags
- Description
- 商品画像URL
- 商品Page URL

ただし「取得できるData」と「正式保存するData」は分ける。

## 6.6 Scenario名候補

商品名からApplication側のRuleでScenario名候補を生成可能。

例：

`CoCシナリオ『○○』SPLL:XXXX`

から、

`○○`

を候補生成。

Ruleで安全に切り出せない場合は、
商品名全文を候補として使用可能。

自動確定しない。

## 6.7 作者候補

Shop名は、

> **作者候補**

として扱う。

Shop名＝作者と断定しない。

Userが確認・修正可能。

## 6.8 Game System候補

BOOTHに専用Game System Fieldが存在することを前提にしない。

以下をRule-basedで解析する。

- 商品名
- Category
- Tags
- Description

既知表記辞書からGame System候補を生成する。

候補はUserが修正・削除可能。

自動確定しない。

判定できない場合は空欄のままとし、
BOOTH取得失敗とは扱わない。

## 6.9 Description

DescriptionはGame System推定等に必要な範囲で一時解析可能。

Description全文はScenario Dataとして保存・転載しない。

既存Scenario Entityに存在しない、

- HO
- プレイ人数
- プレイ時間
- あらすじ
- 推奨技能
- ロスト率
- その他商品説明Data

等を、取得できるという理由だけで正式属性に追加しない。

## 6.10 Scenario URL

Scenario URLが空なら、
入力されたBOOTH商品URLをScenario URL候補として仮反映する。

## 6.11 Image

BOOTH商品画像URLは、

> Scenario画像候補

として取得可能。

ただし正式な表示・保存・参照方式は、
No.27の確定Ruleに従う。

## 6.12 保存しないData

以下は既存Scenario仕様に存在しないため、
MVPでは正式保存しない。

- 価格
- 在庫
- Variation
- 販売状態
- 生HTML
- 生JSON
- その他BOOTH内部Data

## 6.13 Failure

BOOTH取得失敗はScenario登録失敗としない。

Userはそのまま手入力を継続可能。

BOOTH仕様変更により取得不能になっても、
通常Scenario登録機能は利用可能であること。

## 6.14 負荷対策

- Timeout
- Response Size上限
- Request回数制限
- 必要最小限の取得

を行い、
BOOTHへ過度な負荷をかけない。

# 7. No.27 BOOTH外部画像URL表示／外部画像参照機能【確定】

## 7.1 基本思想

外部画像は、

> **User本人のActivity Libraryを視覚的に構成するためのExternal Image Reference**

として扱う。

「画像を取り込んで配布する機能」とは位置づけない。

MVPではSNSのような一般公開機能へ利用しない。

## 7.2 表示範囲

BOOTH等の外部Scenario画像は、

> **Login User本人のLibrary内のみ**

で表示する。

MVPでは、

- 公開Gallery
- SNS Timeline
- 誰でも閲覧できるScenario Page
- Public Share Page

等には表示しない。

## 7.3 保存するもの

外部画像を正式採用した場合、
既存仕様どおり選択された外部画像URLをScenarioの正式画像情報として保存可能。

必要に応じて、
元Scenario商品Page URLをScenario URLとして保持する。

## 7.4 保存しないもの

本Serviceでは外部画像について、

- 画像FileをServerへ複製・恒久保存しない
- Blob / Base64を保存しない
- Backend Proxy画像を作らない
- 自前Thumbnailを生成しない
- 自前CDNへ再配信しない
- 本Service独自の恒久Cacheを作らない

ブラウザ自身の通常Cacheまで禁止するという意味ではない。

## 7.5 表示方式

Browserが外部画像Hostから直接取得する。

概念：

TRPG GAME LIBRARY
→ HTML上で外部URLを参照
→ User Browser
→ BOOTH等の画像Server

## 7.6 画像加工

外部画像は原則、

- Cropしない
- 色変更しない
- 文字を重ねない
- Watermarkを追加しない
- 元画像のLogo / Credit / 作者名を切り落とさない

既存Visual Designでも、
Scenario画像を不要にCropしない方針を維持する。

表示では `object-fit: contain` 等を基本候補とする。

## 7.7 出典導線

Scenario View等から、

> **元Scenario / BOOTH商品Pageへ移動できる導線**

を維持する。

例：

`シナリオページを見る ↗`

外部画像の表示元を自Service作品として誤認させる見せ方を避ける。

## 7.8 利用規約自動解析はしない

BOOTH商品説明やShop規約を自動解析し、

- 合法
- 違法
- 利用可
- 利用不可

を判定する機能は作らない。

以下のKeyword Detectionによる自動除外も行わない。

- 無断転載禁止
- 転載禁止
- 掲載禁止
- その他類似表現

理由：

- 文脈上の例外を誤判定する可能性がある
- 許可条件を誤認する可能性がある
- 高精度な規約解釈はMVPとして実装Costが過大
- Service自身が権利判断者になることを避ける

## 7.9 User同意

外部画像参照機能については、

- 利用規約同意時
- または外部画像機能の初回利用時

などに、

> **一度だけ**

仕組みと利用条件を説明し、同意を得る。

Scenarioごとに毎回Copyright確認DialogやCheckboxを表示しない。

UXを過度に損なわない。

## 7.10 User同意の意味

User同意は、

> 画像の著作権利用許諾を得るものではない。

Userは通常、第三者画像の権利者ではないため、
Userの同意が権利者の許諾を代替するとは扱わない。

同意対象は、

> **外部画像参照機能の仕組みと利用条件**

である。

## 7.11 利用規約へ記載する基本方針

利用規約では少なくとも以下を明示する。

- 外部画像機能は外部Service上の画像URLを参照して表示する機能
- 外部画像の著作権その他の権利は各権利者に帰属する
- 本Serviceは外部画像の利用許諾をUserへ付与するものではない
- Userは掲載元・権利者の定める利用条件を遵守する
- 本Serviceは外部画像Fileを原則として自Serverへ複製・再配布しない
- 権利者等から申出があった場合、対象画像を非表示にできる

## 7.12 権利者からの申出

権利者・掲載元等から、

> 画像表示を停止してほしい

との具体的な申出があった場合：

> **対象画像を暫定的に即時非表示**

にできること。

法的判断が完了するまで表示を継続する必要はない。

非表示後はPlaceholderへ切り替える。

Scenario本体やTable履歴等は削除しない。

## 7.13 全体Kill Switch

BOOTH等の外部Service側から、
外部画像表示方式そのものについて停止要請があった場合に備え、

> **外部画像表示機能全体を一括停止できるKill Switch**

を用意する。

外部画像表示を停止しても、
Scenario / Table / Participation等の活動履歴Dataは維持する。

## 7.14 Privacy / Security

外部画像表示では、

`referrerpolicy="no-referrer"`

等を利用し、
Private LibraryのPage URL等を外部画像Hostへ不要に送らない方向とする。

CSP等により、
許可する画像Hostを必要範囲へ限定する。

任意の不明Hostを無制限に許可する設計にはしない。

## 7.15 非営利・非公開性の位置づけ

本Serviceは現時点で、

- 販売予定なし
- 小規模利用
- User本人のLibrary内で完結
- 一般公開を目的としない

という性質を持つ。

ただし、

> **非営利／非公開だから画像を自由利用できる**

という法的根拠にはしない。

これらはリスク低減要素としてのみ扱う。

# 8. BOOTH画像・素材に関する法務上の整理【確認事項】

## 8.1 スクレイピングと画像利用は別

BOOTHが常識的な範囲でのスクレイピングを許容していても、

> **取得した画像の二次利用が自動的に許可されるわけではない。**

情報取得の可否と、
著作物の利用可否は分離して考える。

## 8.2 外部参照方式

画像Fileを本Service Serverへ保存せず、
外部HostからBrowserへ直接送信させる方式は、

> 自Serviceが画像Fileを複製・再配布する方式とは異なる。

ただし、

> External Image Referenceなら常に合法

という一般的な保証とは扱わない。

## 8.3 利用規約の記載がある場合

商品／Shopの利用規約については、
Application側で自動判定しない。

Userは掲載元の利用条件に従う必要がある。

Service側が具体的な権利問題を認識した場合は、
対象画像を停止可能とする。

## 8.4 配布素材と商品サムネイルは同一扱いにしない

BOOTH上では、

- Web利用可能な配布素材
- ディスプレイ用画像
- Trailer素材
- 商品サムネイル
- 商品説明画像

等が同一Page上に存在し得る。

利用規約によっては、

> 配布素材はWeb利用可だが、商品Pageのサムネイル転載は禁止

という場合もある。

したがって、

> 「同じBOOTH Pageに表示されている画像だから同じ利用条件」

とは扱わない。

ただしMVPでは、
それらの利用許諾をSystemが自動解釈する機能は作らない。

# 9. No.20〜27までの進捗状況
