# 3. サービスの中心コンセプト【確定】

> **すでに存在するTRPG情報を、何度も入力させない**

過去の活動履歴は取り込み、

今後は一度登録した、

- シナリオ
- 人物
- PC

を別の卓でも再利用する。

単なるシナリオ管理サービスではなく、

> **TRPG活動履歴を蓄積し、その情報を次の活動記録にも再利用できるサービス**

として設計する。

---

# 4. UI上の中心と内部データの中心【確定】

UI上の主要な入口は、

```text
シナリオ一覧
↓
そのシナリオで遊んだ卓一覧
↓
卓詳細
```

とする。

一方、内部データでは、

> **Table（卓）が活動履歴の中心**

である。

UIの中心とデータ構造の中心を混同しない。

# 5. ログイン・ユーザー単位のデータ管理【新規確定】

本アプリでは、サービス全体で1つの大きなデータ集合を共有するのではなく、

> **ログインしたUserごとに自分のTRPG活動データを管理する。**

認証には、MVPでは**Googleアカウントによるログインを採用する方向**とする。

独自のID・パスワード認証を自前実装するのではなく、外部認証を利用する。

ただし、

> Google認証を利用することと、アプリ側の認可・データ保護が不要になることは別である。

各データの取得・更新・削除では、

> **ログインUserがそのデータの所有者であることを確認する**

認可設計が必要。

Googleから取得・保存する具体的な項目、OAuth / OIDCの具体的実装方法、トークン管理等は後続の認証・セキュリティ設計で公式情報を確認して確定する。

# 6. Userと「自分自身」のPerson【新規確定】

従来Personに存在した、

- 自分自身かどうか：boolean

は廃止する方向とする。

代わりに、

> **1Userにつき、自分自身を表すPersonを1件紐づける。**

概念上は、

```text
User
└ SelfPerson → Person
```

とする。

初回ログイン時は、

```text
Googleログイン
↓
User作成
↓
TRPG上で使用する自分の表示名を確認・入力
↓
自分自身を表すPersonを作成
↓
UserとSelfPersonを紐づけ
```

という流れを基本とする。

Googleアカウント上の氏名をTRPG上の表示名として強制しない。

Google表示名を初期候補として使うかどうかは、画面設計・認証設計時に確定する。

# 8. Userの所有関係【確定方針】

MVPでは、以下をUserごとの管理データとする。

```text
User
├ 0..N Scenario
├ 0..N Person
├ 0..N PC
└ 0..N Table
```

つまり、Scenario・Person・PC・Tableは各Userに属する。

別Userが同じシナリオ名・同じ人物名・同じPC名を登録しても、MVPでは別データとして扱う。

TableDate・Participation・EndPcStateは、親データから所有Userを辿る。

```text
TableDate
→ Table
→ User

Participation
→ Table
→ User

EndPcState
→ Participation
→ Table
→ User
```

これら子エンティティへUserIDを重複して持たせるかどうかは、物理DB設計時に最終判断する。

# 9. Scenario【確定】

## 主な属性

- ScenarioID
- User：必須
- シナリオ名：必須
- 作者名：任意
- URL：任意
- ゲームシステム：任意

ゲームシステムは、

> **候補＋自由入力**

方式。

## 重複

以下は一意にしない。

- シナリオ名
- URL

重複候補を案内したうえで、

- 既存を使う
- 新規登録する

をユーザーが選択できる。

自動統合しない。

## 削除

関連Tableが0件なら削除可能。

関連Tableが1件以上なら削除不可。

削除可能な場合も、削除前にユーザー確認を行う。

Scenario削除によってTableを自動削除しない。

Scenario → TableへのCASCADE DELETEは行わない前提。

論理削除・ゴミ箱・復元はMVPでは採用しない。

---

# 10. ScenarioFavorite【新規確定】

お気に入りはScenario本体の属性にしない。

> **User × Scenarioの関係データ**

として保持する。

MVPでは概念上、

```text
ScenarioFavorite
- UserID
- ScenarioID
```

とする。

ルール：

```text
レコードあり
→ そのUserにとってお気に入り

レコードなし
→ お気に入りではない
```

`UserID + ScenarioID` の組み合わせは一意にしてよい。

お気に入り登録・解除によってScenario本体を更新しない。

---

# 11. Person【更新確定】

## 主な属性

- PersonID
- User：必須
- 表示名：必須

従来の、

- 自分自身かどうか

はUser.SelfPersonとの関係へ置き換える。

MVPでは以下を保持しない。

- Discord ID
- SNS ID
- メール
- 本名
- 詳細プロフィール

同名Personは許可。

Person本体の削除仕様は、現時点では未確定。

# 12. PC【更新確定】

## 主な属性

- PCID
- User：必須
- PC名：必須
- 現在紐づくPerson：必須
- ゲームシステム：任意
- 外部キャラクターシートURL：任意

## MVP対象外

- PC画像
- 技能一覧
- 詳細ステータス

## 状態値

SAN・HP・MP等の現在値をPC本体へ恒久保存しない。

各卓のParticipationに紐づくEndPcStateとして履歴保存する。

## Person変更

PCの現在の紐づくPersonを変更しても、過去卓を自動変更しない。

そのため、

```text
現在のPC所有者：B

過去Participation
人物：A
PC：X
```

を許容する。

Participation.personとPC.personの一致をDBで強制しない。

# 13. PC本体の削除【新規確定】

PCそのものの削除をMVPへ追加する。

UC10は、

> **PC情報を登録・確認・修正・削除する**

へ拡張する。

削除ルール：

```text
関連Participationが0件
↓
ユーザーへ削除確認
↓
PC本体を削除可能
```

```text
関連Participationが1件以上
↓
PC本体は削除不可
```

関連Participationが存在するPCを削除するために、

- Participationを自動削除しない
- Participation.PCIDを自動NULLにしない
- EndPcStateを自動削除しない

ものとする。

PCの論理削除・ゴミ箱・復元はMVPでは採用しない。

# 14. Table【更新確定】

Tableは、

> **一つのシナリオについて行われた、一連のTRPG活動**

を表す。

複数日にわたって遊んでも、一連の活動であれば1卓。

参加者0人でも登録可能。

実施日0件でも登録可能。

## 主な属性

- TableID
- User：必須
- Scenario：必須
- TableName：任意【今回追加】
- 録画URL：任意
- 登録日時：必須・システム自動記録

---

# 15. 卓名 TableName【新規確定】

ユーザーは卓ごとに任意の名前を付けられる。

例：

- 第二陣
- 身内卓
- 高校同期卓

TableNameは任意であり、未入力でも登録可能。

## 未命名卓

TableNameが未入力の場合、

```text
卓1
卓2
卓3
```

のようにシステムが表示する。

ただし、

> **「卓1」等はDBへTableNameとして保存しない。**

未命名卓の現在の一覧から画面表示時に自動採番する。

未命名卓が削除された場合は表示番号を詰め直す。

例：

```text
卓1
卓2
卓3
```

から卓2を削除した場合、

```text
卓1
卓2
```

と表示する。

---

# 16. 卓名の入力UI【確定方向】

卓名入力時には、「卓1」等を実値として入力済みにするのではなく、

> **未入力時のデフォルト表示・placeholder相当**

として扱う。

ユーザーが文字を入力すると、デフォルトの「卓1」等が消え、任意の卓名を簡単に入力できるUIとする方向。

具体的な実装・文言は画面設計時に確定する。

---

# 17. 卓一覧の並べ替え【新規確定】

卓一覧には並べ替え機能を設ける。

少なくとも、

> **ユーザーがTableNameを入力した卓を優先して上位表示できる並べ替え**

を可能にする。

例：

```text
第二陣
身内卓
卓1
卓2
卓3
```

並べ替えによって未命名卓の番号算出基準を無秩序に変えない。

具体的な並べ替え候補は画面設計時に確定する。

---

# 18. TableDate【確定】

Tableは、

> **0件以上のTableDate**

を持つ。

各TableDateは、

- TableDateID
- Table：必須
- 実施日：必須

を持つ。

TableDateが0件なら日付不明卓。

実施日にNULLを持つTableDateを作る必要はない。

## 時系列判定

TableDateが存在する場合、

> **そのTableの最も新しいTableDate**

をその卓の時系列上の基準日として優先する。

---

# 19. Tableの登録日時【確定】

登録日時は、

> **その卓をサービスへ登録した日時**

である。

TableDateが存在しない場合に限り、

> **時系列を判断するための低精度な参考値**

として利用できる。

ただし、

> 登録日時 = 実際に遊んだ日時

とはみなさない。

過去卓を後日登録する場合があるため、登録順とプレイ順は一致しない場合がある。

---

# 20. Participation【確定】

Participation 1件は、

> **1人の人物が、その卓で1つの役割・0〜1件のPCを担当した記録**

とする。

## 主な属性

- ParticipationID
- Table：必須
- Person：必須
- Role：必須
- PC：任意
- HO：任意

RoleはMVPでは、

- KP
- PL

を扱う。

同じ人物が同じ卓に複数Participationを持てる。

同じPCを同じ卓で複数Participationが参照することもDBでは禁止しない。

Table + Personを一意にしない。

Table + PCを一意にしない。

---

# 21. EndPcState【確定】

EndPcStateは、

> **1件のParticipationにつき0〜1件**

保持する。

## 主な属性候補

- EndPcStateID
- Participation：必須
- SAN：任意
- HP：任意
- MP：任意
- 成長：任意
- 生還／ロスト：任意
- 後遺症等：任意

すべて任意。

ParticipationにPCが設定されていない場合、

> **EndPcStateを保持不可。**

ParticipationにPCが1件設定されている場合のみ、

> **EndPcStateを0〜1件保持可能。**

---

# 22. 卓内のPC解除・変更【更新確定】

PC本体の削除とは別に、

> **特定の卓のParticipationからPCだけを外す**

ことは可能。

PCとの紐づけを解除する場合、そのParticipationに存在するEndPcStateも一緒に解除する。

解除前にはユーザー確認を行う。

## PC-A → PC-Bへ変更する場合

PC-Aに紐づいていたEndPcStateを、そのままPC-Bへ引き継がない。

変更時は、

1. PC変更によって既存EndPcStateも解除されることを確認
2. 既存EndPcStateを解除
3. PC-Bを設定
4. 必要ならPC-B用のEndPcStateを新しく入力

とする。

---

# 23. 継続PCの前回状態判定【確定】

継続PC利用時は、過去のEndPcStateを入力補助として表示する。

## TableDateがある場合

対象卓より前の実施日を持つ履歴から、

> **時系列上最も新しいEndPcState**

を優先する。

1卓に複数TableDateがある場合は、その卓の最も新しいTableDateを基準にする。

## TableDateがない場合

Tableの登録日時を、

> **低精度な参考情報**

として利用できる。

登録日時しか根拠がない場合は、

> 実施日不明のため登録順を参考にしている

ことを区別して扱う。

DBへ最後に登録されたEndPcStateを、そのままPCの現在値とは扱わない。

# 26. UC01〜03 インポート【確定整理】

UC01を、

> **既存データの取り込みから正式登録までを統括する親UC**

として扱う。

```text
UC01 既存履歴を取り込む
↓
UC02 取り込み結果を確認
↓
必要ならUC03で欠損・不明箇所を修正
↓
ユーザーが登録対象を確定
↓
UC01の処理として正式データへ登録
```

UC02・UC03で編集する候補データは、原則として正式9エンティティではなくインポート中の一時データ。

一時データのCRUDは、正式データのCRUD表へ混ぜない。

# 28. UC05〜08の役割分担【確定整理】

## UC05

> 新しく遊んだ卓を登録する。

活動履歴を成立させる主UC。

Table・TableDate・Participation・EndPcStateの作成を担当する。

Scenario・PCの新規作成そのものは、それぞれUC09・UC10の処理として扱う。

Personは独立管理UCがないため、新規参加人物の作成はUC05内で扱う。

## UC06

> 登録済みScenarioを新しい卓で再利用する。

ScenarioのReadが中心。

Table作成はUC05が担当する。

## UC07

> 登録済みPCを新しい卓で再利用する。

PC・過去Participation・Table・TableDate・EndPcState等をReadし、継続PC候補・前回状態を確認する。

今回のParticipation作成はUC05が担当する。

## UC08【MVP復帰】

> 最近使用した情報を使って卓を登録する。

最近使った、

- Scenario
- PC
- 同卓者Person

等を候補提示し、卓登録の入力負担を下げる。

高度な推薦アルゴリズムはMVPでは前提としない。

「最近」の具体的な判定ルールは後続の処理設計で確定する。

既存のTableDate優先・登録日時は低精度参考値という時系列ルールを流用する案が有力だが、現時点では処理詳細として未確定。

# 30. UC10 PC管理【更新確定】

UC10：

> **PC情報を登録・確認・修正・削除する**

PCのPerson変更時は過去卓を自動変更しない。

PCが使用されている過去卓を確認できるようにする。

ユーザーが特定の過去ParticipationからPCを解除した場合のみ、そのParticipationを更新する。

PC解除時はEndPcStateも削除する。

PC本体削除は関連Participationが0件の場合のみ可能。

# 31. UC11 シナリオから過去卓確認【確定】

Scenarioを入口として、そのScenarioに紐づくTable一覧を確認する。

TableNameが設定されている場合はその卓名を表示できる。

未設定時は「卓1」「卓2」等を表示する。

具体的に一覧へ表示する日付・参加者等は主要画面設計時に確定する。

今回の検索・絞り込み・並べ替え機能の主要UC。

少なくとも、

- 検索
- PL参加のみ
- KP参加のみ
- お気に入りのみ
- 並べ替え

を扱う。

お気に入り登録・解除はScenarioFavoriteを通して行う。

Scenario本体にはお気に入りフラグを持たせない。

- TableDate

- PC
- EndPcState

を確認する。

# 35. UC17 自分のTRPG活動を振り返る【MVP復帰】

MVPでは簡易版を採用する。

まずは以下のような集計を想定する。

- 遊んだシナリオ数
- 参加した卓数
- PL参加回数
- KP参加回数

ログインUserのSelfPersonを基準に集計する。

## 将来拡張

月別・年別の活動集計へ拡張できる余地を残す。

例：

```text
2026年
├ 1月：5卓
├ 2月：3卓
└ 3月：7卓
```

ただし、TableDateがない卓について登録日時を実施年月として扱わない。

月別・年別集計を実装する際は、

> 実施日不明卓を別扱いする

等のルールを別途確定する。

# 36. MVP外を維持するUC・機能

現時点では以下をMVP必須へ戻さない。

## UC15
複数の履歴をまとめて編集する。

価値はあるが、一括変更時の確認・失敗処理・事故防止等の実装量が増えるためMVP外。

## UC16
卓にメモ・感想を残す。

入力負担増と中心コンセプトへの優先度からMVP外。

## UC18
一回の卓を他者と共有する。

公開範囲、第三者情報、HO秘匿、アクセス制御等の設計範囲が広いためMVP外。

# 37. 現在の概念ER関係【最新版】

概念上は以下。

```text
User
│
├── SelfPerson ───────────── Person
│
├── 0..N Scenario
│       │
│       ├── 0..N Table
│       └── 0..N ScenarioFavorite
│
├── 0..N Person
│       ├── 0..N PC
│       └── 0..N Participation
│
├── 0..N PC
│
└── 0..N Table
        │
        ├── 0..N TableDate
        │
        └── 0..N Participation
                   │
                   └── 0..1 EndPcState

User 1 ── 0..N ScenarioFavorite
Scenario 1 ── 0..N ScenarioFavorite
```

既存関係：

```text
Scenario 1 ── 0..N Table

Table 1 ── 0..N TableDate

Table 1 ── 0..N Participation

Person 1 ── 0..N Participation

Person 1 ── 0..N PC

PC 1 ── 0..N Participation
Participation側からPCは0..1

Participation 1 ── 0..1 EndPcState
```

EndPcStateを保持できるのは、ParticipationにPCが存在する場合のみ。

# 40. 削除関係【最新版】

## Scenario削除

関連Tableが0件なら、ユーザー確認後に削除可能。

関連Tableが1件以上なら削除不可。

Tableを連鎖削除しない。

## PC削除

関連Participationが0件なら、ユーザー確認後に削除可能。

関連Participationが1件以上なら削除不可。

ParticipationやEndPcStateを自動変更・削除しない。

## Table削除

削除：

- Table
- TableDate
- Participation
- EndPcState

残す：

- Scenario
- Person
- PC

## Participation削除

EndPcStateが存在すれば一緒に削除。

## ParticipationからPC解除・変更

既存EndPcStateも解除。

ユーザー確認を行う。

# 41. 外部キャラクターシート等【維持】

外部キャラクターシートURLはPCの参照先として保存する。

URLだけからPC情報を自動取得できることはMVP前提にしない。

ユーザーが取得したキャラコマJSON等を任意の入力補助として利用する方向。

取得する場合も必要な情報だけ扱う。

例：

- PC名
- キャラクターシートURL
- SAN
- HP
- MP

HO秘匿・メモ等、不要情報を保存しない。

外部画像の自動取得・自動保存はMVPでは行わない。

具体的なAPI・利用規約は、対応サービス確定後に公式情報を確認する。

# 43. Google認証に関する法務・セキュリティ方針【現段階】

MVPではGoogle認証を採用する方向。

ただし具体実装前に、Google公式情報を確認する。

原則：

- 必要最小限の情報・権限だけ取得する
- Googleの氏名をTRPG上の表示名として強制しない
- 認証用情報を他ユーザーへ表示しない
- 認証後もUser所有権による認可を行う
- 他UserのScenario / Person / PC / Table等へアクセスさせない
- アカウント削除時のデータ削除方針は後続設計で決める
- プライバシーポリシー等の必要性も本番公開条件に応じて確認する
