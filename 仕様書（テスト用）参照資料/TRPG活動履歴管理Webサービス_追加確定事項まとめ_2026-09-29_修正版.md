# 2. Person削除条件【確定】

Personは、次の条件をすべて満たす場合のみ削除可能とする。

- UserのSelfPersonではない
- 関連PC件数が0件
- 関連Participation件数が0件

削除時にCascadeでPC / Participationを書き換えたり、別Personへ自動再割当したりしない。

SelfPersonの削除は通常Person削除では扱わず、Account削除フローで扱う。

# 3. KP / SKPの再構築方法【確定】

Roleとして `SKP` を新設しない。

`isMainKP` 等の専用Booleanも追加しない。

同一Table・同一Role内で表示順を持ち、Role = KP のParticipationについて、

- 最初 / 最小順のParticipation → UI上「KP」
- それ以降 → UI上「SKP」

として表示する。

SKPをKPへ昇格する場合はRoleを書き換えるのではなく、KP Participationの表示順を並べ替える。

同じ仕組みをPL側の表示順へ拡張可能とする。

# 5. Game System Profile【概念採用・確定】

SAN / HP / MP等を全Game System共通の固定Statusとして扱わない。

既知Game Systemについては、内部のCanonical System KeyとGame System Profileを使用する。

概念例：

```text
GameSystemProfile
- 表示するStatus
- Status Key
- Label
- 表示順
- Input Type
```

EndPcState側は、固定 `san / hp / mp` カラム前提ではなく、Profileに応じた汎用Status値を保持できる構造を採用する。

既知System例：

```text
gameSystemKey = "coc_7e"
```

自由入力された未知Game Systemは、システムが勝手に既知Systemへ推測Mappingしない。

### Visual
PC Focus v5.9のSTATUS Visualは維持し、Profileに応じて中身だけを可変にする。

- ProfileをDB Entity / Master / Application Configのどれとして実装するか

特に「過去EndPcStateの歴史的解釈固定」は、最終Frontend / Backend / API / Data仕様書作成前に必ず解決する。

# 11. PC / Scenario Upload画像仕様【確定】

## 対応形式
- JPEG
- PNG
- WebP

## 非対応（MVP）
- GIF
- SVG
- HEIC / HEIF
- AVIF

## 容量
- 1画像 最大10MB

## Validation
拡張子だけを信用せず、Backendで実画像としてDecode可能か確認する。

## 画像品質・非破壊方針
- EXIF Orientationを正規化
- Aspect Ratioを維持
- 自動Cropしない
- 小さい画像を無理にUpscaleしない
- PNG等のAlpha透明を維持
- Uploadされた原本はLossless Masterとして安全に保持
- Web表示用の最適化Derivativeを別生成
- Derivativeは目視で粗さが問題にならない品質を維持
- PC画像のDrag / Zoom / Positionは表示Metadataであり、Masterを破壊的Cropしない

## 差し替え
新しいMaster / Derivativeの保存とDB更新がすべて成功した後に、旧画像を削除する。

失敗時は旧画像を維持する。

## Storage
本番ではObject Storage等のFile Storageを使用し、画像Binaryを通常DBカラムへ直接保持しない。

## 削除
Entity削除・Account削除時にはUser所有Upload画像を物理削除対象とする。

外部URL画像は自サービスが物理削除する対象ではない。

### 後続実装で決めるもの
- 具体Storage製品
- Encoder
- Quality値
- Derivative最大辺等

# 13. Import一時Data構造【確定】

正式9Entityとは分離したImport専用一時Dataとして、以下の基本構造を採用する。

```text
ImportSession
│
├─ ImportSource
│   ├─ File
│   └─ Pasted Text
│
├─ ImportCandidate
│   ├─ candidateData
│   ├─ status
│   ├─ confirmationStatus
│   ├─ registrationTarget
│   ├─ registrationStatus
│   ├─ registrationResult
│   └─ version
│
└─ ImportCandidateSourceTrace
    ├─ Candidate
    ├─ Source
    └─ source location
```

## Source Trace
1 Candidateが複数Source / 複数Rangeから生成される可能性に対応するため、CandidateとSourceを1対1固定にしない。

Split / Merge後も元Dataを追跡できるようにする。

## 正式登録結果
Candidateには、正式登録結果を識別できる情報を保持し、再試行時の二重登録防止に利用する。

`registrationResult` の正確な物理表現はJSON固定ではなく、

> 正式登録済みIDを追跡し、Idempotencyを確保できる構造

という概念を確定事項とする。

## Auto Save競合
複数Tab等からの古い更新で上書きしないよう、Versionを持たせOptimistic Lock相当の競合検出を行う。

## 元Source保存
- 直接貼付Text → 一時Text Dataとして保持可能
- Upload File → Private Temporary File / Object Storageへ保存し、DBは参照Key中心

すべてをDB Binaryへ詰め込まない。

# 14. Import解析Algorithm【確定】

生成AI / LLMをMVPの必須解析経路には使用しない。

ただし、**推定・自動入力はImportの必須仕様**として維持する。

## Pipeline

```text
入力
↓
形式別構造解析
↓
共通中間構造
↓
共通推定
↓
卓Candidate
↓
確認・修正
↓
正式登録
```

## 対象
- CSV
- Markdown
- HTML
- TXT等のText
- 直接貼付Text
- PDF / OCRはMVP外

## 共通推定対象
中核：
- Scenario名
- 実施日
- Person
- KP / PL
- PC名

存在する場合：
- Game System
- HO
- 録画URL
- その他既存正式項目として安全に対応できるData

## 推定の積極性

```text
項目分類
→ 比較的積極的

値境界
→ 慎重

Data同士の関係付け
→ より慎重

Tableの分割・統合
→ 非常に慎重
```

## 自動入力
明確に推定できる値はImportCandidateへ自動入力する。

曖昧な値は、
- 要確認
- 未割当
- 修正必要

として残し、勝手に正式確定しない。

## 既存Data照合
既存Scenario / Person / PCは強い判断材料として利用する。

PC照合では、

> **PC名 + Person候補**

を強い材料とする。

ただし、
- 同名Scenarioを自動統合しない
- 同名Personが1件だけでも自動統合しない
- PC候補もUser確認なしで正式統合しない

「自動入力」と「正式Dataへの自動統合」は明確に分ける。

## HTML
HTMLをBrowserとして実行しない。

- script実行禁止
- Event Handler実行禁止
- 外部Resourceを自動取得しない
- DOM / Text Structureとしてのみ解析

## AI
MVP外：
- 高度なAI学習
- Userごとの推定学習
- 完全自動重複統合

将来、Rule-based解析で要確認となったDataへの補助として追加可能な余地は残す。

## 具体Library
CSV / HTML / Markdownの具体Parser Library名はBackend技術Stack決定後に選定する。

# 16. Import正式登録Transaction【確定】

Transaction単位は **1 ImportCandidate** とする。

## Candidate内
1 Candidateから今回新規作成する正式Data一式はAtomicに登録する。

例：

```text
Candidate A
├ Scenario（新規 or 既存参照）
├ Person（新規 or 既存参照）
├ PC（新規 or 既存参照）
├ Table
├ TableDate
├ Participation
└ EndPcState
```

途中失敗時、そのCandidate分だけRollbackする。

中途半端にScenarioだけ作成済み等の状態を残さない。

## 複数Candidate一括登録

```text
Candidate A → COMMIT
Candidate B → COMMIT
Candidate C → ROLLBACK
```

とし、C失敗を理由にA / Bまで巻き戻さない。

## 共有正式Data
複数Candidateが同じ新規Scenario / Person / PC等を参照する場合は、最初の正式登録結果のIDをImport内部Mappingで再利用し、重複生成しない。

## Idempotency
正式Data作成とCandidateの登録済み状態 / 結果記録は可能な限り同一Transactionで確定する。

通信断等でFrontendから失敗に見えて再試行されても、すでに登録済みCandidateを再度新規登録しない。

## 用語区別
- 一部登録：Userが意図的に一部Candidateだけ登録する既存仕様
- 部分成功：選択したCandidate群の一部だけ技術的に成功する状態

両者を混同しない。

# 17. CSV文字コード【確定】

MVP対応：

- UTF-8（BOMなし）
- UTF-8（BOMあり）
- Windows-31J / CP932

UI上は必要に応じて「UTF-8 / Shift_JIS」と分かりやすく表記できる。

## Decode順

```text
1. BOM確認
2. UTF-8として厳密Decode
3. 失敗時、CP932として厳密Decode
4. それも失敗 → Encoding Error
```

Decode不能文字を `�` 等へ置換して強行解析しない。

UTF-8 BOMはHeader名へ混入しないよう除去する。

Decode後は内部Unicode / UTF-8相当へ統一し、以降のCSV Parser / 共通推定をEncoding非依存にする。

MVP非対応：
- EUC-JP
- ISO-2022-JP
- UTF-16 LE / BE
- その他Encoding

# 18. Import完了後48時間削除【確定】

既存仕様：
- 進行中ImportSession → 最終保存から7日保持、保存成功ごとに延長
- 完了後の元Import Data → 48時間保持後に削除
- 正式登録済み9Entity → 削除しない
- Account削除時 → 48時間を待たない

## 完了時

```text
completedAt
deleteAfterAt = completedAt + 48h
status = COMPLETED
```

を記録する。

## Cleanup
Backendで原則1時間ごとのCleanup Jobを実行する。

```text
status = COMPLETED
AND currentTime >= deleteAfterAt
```

のSessionを削除対象とする。

したがって、物理削除は48時間経過後から最大おおむね1時間以内を想定する。

## 削除対象
- ImportSession
- ImportSource
- ImportCandidate
- ImportCandidateSourceTrace
- Temporary Upload File
- 貼付Text
- 解析結果
- 推定結果
- 修正状態
- Source Trace
- Import内部Mapping / registrationResult等

正式9Entityは絶対に削除対象へ含めない。

## Reliability
Cleanupは、
- Idempotent
- Retry可能
- 1Session失敗で他Sessionを止めない

構造にする。

必要に応じて内部 `DELETE_PENDING` 相当状態を利用可能。

## Account削除
当該UserのImport一時Dataを即時削除対象へ送る。

物理Storage削除が一時失敗しても、Userから再アクセス不能にし、Cleanupで再試行する。

# 19. Google由来User属性【確定】

MVPでGoogleから永続保存する認証由来情報は、Google Account一意識別子 `sub` のみを基本とする。

物理DBでは将来Provider追加を考慮し、

```text
User
- id
- authProvider
- providerSubject
- selfPersonId
- createdAt
- updatedAt
```

のようなProvider非依存構造を採用する。

MVP：

```text
authProvider = GOOGLE
providerSubject = Google sub
```

`(authProvider, providerSubject)` は一意として扱う方向。

## User DBへ永続保存しないGoogle属性
- email
- email_verified
- name
- given_name
- family_name
- picture
- locale
- hd
- その他MVP業務に不要なGoogle Profile Data

## Google表示名
初回SelfPerson設定時に候補として一時利用することは可能。

Userが採用した文字列だけを、

```text
SelfPerson.displayName
```

として保存する。

Google表示名自体をUser Entityへ恒久複製しない。

## 所有管理
Google `sub`は認証Accountとの紐付けにのみ使用する。

Scenario / Person / PC / Table等の所有権管理は内部 `User.id` を使う。

# 20. Google OAuth / OIDC / Session管理【確定】

## Frontend
Google Identity Services（GIS）の **Sign in with Google Button** を使用する。

MVPでは、
- One Tapを使用しない
- Auto Selectを使用しない

## Login Flow

```text
Browser
↓
Google Sign in
↓
Google ID Token
↓
Backend Auth Endpoint
↓
BackendでID Token検証
↓
providerSubject(sub)からUser特定
↓
App独自Session発行
↓
以後はApp SessionでAPI利用
```

Google ID Tokenを毎回の業務API認証Tokenとして使い続けない。

## Backend Token検証
Frontendから送られた `sub` 文字列を直接信用しない。

BackendでGoogle ID Tokenについて少なくとも以下を検証する。

- 署名
- issuer
- audience
- expiration
- Token妥当性
- subject (`sub`)

## Google Token保存
MVPでは、
- Google ID Token
- Google Access Token
- Google Refresh Token

をアプリDBへ恒久保存しない。

認証目的で検証後、App独自Sessionへ切り替える。

## App Session
Server-side Sessionを基本とする。

Browser側には推測困難なOpaque Session IDをCookieで保持する。

Cookieは原則：

```text
HttpOnly
Secure
SameSite=Lax
```

認証TokenをLocalStorageへ保存しない。

## Session期限
Google ID Tokenの寿命とApp Session寿命を分離する。

App Sessionには明示的な有効期限を持たせる。

具体的な期間値はBackend / Security詳細設計で最終決定する。

Session切れ時は既存仕様どおり、
- 入力Dataを即破棄しない
- 再Login導線を表示
- 可能なら再認証後に元画面 / Draftへ復帰
- 未認証状態でAPI操作を許可しない

## Logout
- Server Sessionを無効化
- Session Cookieを削除
- Google AccountそのものからLogoutさせない

## Account削除時の再認証
削除直前にGoogle認証を改めて実行する。

Backendで、その認証結果の `sub` が現在Userの `providerSubject` と一致することを確認する。

「必ずGoogle Passwordを再入力させる」とは仕様化しない。

## CSRF / Security
- Google認証EndpointではGoogle公式方式に沿ってCSRF対策
- App Session確立後もCookieだけを理由に安全とみなさない
- SameSite
- Same-origin
- Origin検証
- 必要に応じたCSRF Token

等をBackend Security設計で適用する。

## Library
Frontend LibraryはGoogle Identity Servicesを採用。

Backendの具体Token検証Library名は、Backend技術Stack決定後にGoogle公式 / 公式推奨Libraryから選定する。
